Paginate with deterministic ordering or aggregate at the database; require all pages or fail honestly.

## Public booking — repaired locally with actual-handler regressions

- **P1 — Anonymous responses exposed existing patient identity.** POST creation and idempotent replay returned the private appointment row, including paciente_id and crm_pacientes/name, even when the requester supplied a different name and only an unverified matching email. All public appointment responses now use the same explicit DTO: id, inicio_en, fin_en, estado. The frontend consumes only these fields plus booking.professional_name; its current contract is preserved. Internal professional endpoints still retain their complete rows.
- **P1 — Unverified contact could modify an existing chart.** A requester knowing a patient's email could fill that patient's blank telephone, or a telephone match could fill a blank email. The existing-patient branch no longer updates chart contacts. It still creates the pending booking and assignment using the matched patient internally; this change does not introduce or claim identity verification. Staff must resolve identity/contact disagreements. New-patient creation behavior is unchanged.
- **P2 — Direct POST bypassed the published maximum date.** GET advertised and enforced a 45-day default window but POST accepted a valid opening-hours slot in 2040. POST now applies the same configured local-date bounds before availability checks or writes, after idempotent recovery so an existing request remains recoverable later. No new request is accepted beyond the window; the maximum day remains inclusive.

Before repair, `node --test test/public-booking-security.test.js` failed both tests against the actual route handler. After repair it passes 2/2: DTO creation/replay/recovery, no contact mutation, no duplicate recovery writes, historical recovery after the booking window, inclusive maximum and rejection on the following day across winter/summer clock changes. Calendar persistence and retry code paths are otherwise unchanged; no remote Calendar execution was performed.

The existing local SQL rehearsals use fixed 2040/2041 fixtures, so `scripts/test-booking-retries.mjs` and `scripts/test-calendar-persistence.mjs` now freeze the clock only while invoking the public booking handler and restore it in finally. ## Additional confirmed local transport/observability findings

- **P2 — n8n response body escapes the copilot deadline.** `backend/src/routes/agent.js`, n8n fetch/parse boundary: the manual timer is cleared after headers arrive and before parseAgentResponse reads the body. Actual resolveAgentConversation with a 5 ms timeout is still pending after 35 ms with its signal un-aborted when a synthetic fetch sends headers and stalls its body. The root reviewer has been notified; proposed minimal fix is keeping parsing inside the same timed try/finally and controlled fallback catch. No real n8n outage was invoked.
- **P2 — Non-atomic audit failures are silent.** `backend/src/lib/audit.js`, recordAudit catch/error paths: actual recordAudit returns ok:false and emits zero server warnings/errors when its synthetic storage operation fails. Existing callers ignore the result, allowing clinical or patient writes without an observable failure signal. Critical recommendation approvals and invoice issuance use separate atomic SQL audit paths. A policy decision is needed before making those other writes fail or adding a durable fallback; a sanitized server warning is the smallest observability improvement.
- **Runtime limit — Supabase client has no application deadline.** `backend/src/lib/supabase.js`: actual SDK select starts fetch with no AbortSignal and remains pending while a synthetic transport is stalled for 25 ms. This confirms absence of an application-level request deadline, not a failure or an infinite timeout in a live provider. Choosing per-operation deadlines and treatment of uncertain writes is a separate cross-cutting decision; never add blind mutation retries.
